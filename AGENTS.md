# Правила работы с decopaint.fi

## Цель

Развивать интернет-магазин без потери заказов, данных клиентов, индексации и работоспособности платёжных и логистических интеграций.

## Обязательный порядок

1. Зафиксировать исходное состояние и метрики.
2. Работать в отдельной ветке и на закрытом staging.
3. Перед изменением БД создать проверяемый backup.
4. Выполнить автоматические и ручные тесты.
5. Развертывать небольшими партиями с планом отката.
6. После релиза проверить checkout, оплату, письма, Merchant Center и аналитику.

## GitHub-first

- GitHub является единственным источником истины для кода, тестов, документации и контролируемых исходных материалов.
- Каждое изменение сайта начинается с GitHub issue или явно зафиксированной GitHub-задачи.
- Работать только в отдельной ветке; прямые коммиты и push в `main` запрещены.
- Каждое изменение проходит commit, push, pull request, CI и review до слияния.
- На staging и production развёртывается точный commit из GitHub; ручные правки файлов на сервере запрещены.
- Production-развёртывание, изменение БД и внешних сервисов требуют отдельного подтверждения владельца.
- Если GitHub недоступен или репозиторий не синхронизирован, остановить изменение сайта и сначала восстановить GitHub-процесс.

## Запрещено без отдельного согласования

- менять production БД, заказы, клиентов, налоги, цены, остатки или доставку;
- менять Paytrail/PostNord callback, расчёт итоговой суммы или статусы заказов;
- удалять товары из Merchant Center;
- публиковать staging без авторизации и `noindex`;
- копировать production PII в staging;
- хранить ключи, пароли, OAuth JSON или резервные копии в репозитории;
- выполнять необратимые миграции или массовые изменения контента.

## Безопасность

- Секреты только в переменных окружения или секретном хранилище.
- Логи не должны содержать имя, email, телефон, адрес, POST/GET payload, подписи и токены.
- Все операции изменения состояния принимают POST и проходят CSRF/подпись/авторизацию.
- Доступ к заказу всегда проверяется по владельцу или административной роли.
- Для callback обязательны проверка подписи, допустимого статуса, суммы, валюты и идемпотентность.

## Качество

- Python: форматирование, lint, unit/integration tests и `django check --deploy`.
- Frontend: keyboard navigation, видимый focus, alt, контраст, корректные heading и responsive.
- SEO: self-canonical, уникальные title/description, JSON-LD без расхождения с видимым контентом.
- Analytics: события не содержат PII; `purchase` отправляется один раз на подтверждённую оплату.
- Производительность: не ухудшать mobile LCP, CLS и размер критических ресурсов.

## Документация

Каждое изменение обновляет:

- `docs/changelog.md`;
- релевантный audit/plan;
- `docs/deployment.md` и `docs/rollback.md`, если меняется выпуск;
- тест-кейсы в `docs/testing.md`.

## Definition of Done

- изменение проверено на staging;
- есть тест и измеримый критерий успеха;
- security/privacy review пройден;
- backup и rollback готовы;
- production smoke-тест завершён;
- метрики и ошибки проверены после релиза.
